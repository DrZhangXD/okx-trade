## Lessons learned from Plans 1–3 (apply to Plans 4–6)

These are the patterns/gotchas the next agent should know:

### 1. Branch discipline

Every implementer subagent dispatch must include in its prompt:
> Verify `git branch --show-current` shows `<feature-branch>`. NEVER switch branches via `git checkout`. If wrong, STOP and report BLOCKED.

Plan 1's T9 had a subagent silently switch to `main` and commit there. We caught it post-hoc with `git revert` + cherry-pick, but it cost a fix-loop. Be explicit.

### 2. NT BacktestNode injection pattern

The original Plan 1 spec proposed injecting state into running strategies via `node.get_engines()[0].trader.strategies()` AFTER `run_backtest_with_node()` returned. **This does not work** — the node has already finished running by then.

The pattern that worked (Plan 1 T8.5): add a **config field** (e.g. `funding_panel_parquet_path: str | None`) to the strategy's Config. Have the strategy's `on_start` read the parquet on disk and call its own `feed_*` method during startup. Backtest CLI just passes the path string in `ImportableStrategyConfig`. This works because NT calls `on_start` before the engine runs.

Plans 4–6 should use the same pattern: any state injection happens in `on_start`, sourced from a config field (parquet path / pickle path / etc.).

### 3. Combined implementer dispatches save tokens

For tasks that touch the same file, dispatch them combined:
- Plan 2 T1+T2 (both extend `orderbook_data.py`) — one dispatch, two commits.
- Plan 3 T1+T2+T3 (config field + provider + live_node forwarding) — one dispatch, one commit.
- Plan 3 T6+T7+T8 (capture script + strategy hook + CLI) — one dispatch, three commits.
- Plan 3 T9+T10 (integration test + roadmap doc) — one dispatch, two commits.

A single dispatch with multiple commits is cheaper than three separate dispatches with full context briefing each.

### 4. Combined spec+code reviews are fine

Each task has both a spec compliance check and a code quality check. Combining them into one reviewer subagent prompt halves the review cost and produces good-enough quality. Just be explicit in the prompt that you want both checks.

### 5. Strategy file names ≠ class names

Several strategies have surprising class names:
| File | Class actually named |
|------|----------------------|
| `funding_cross_section.py` | `FundingXSStrategy` / `FundingXSConfig` |
| `funding_skew_momentum.py` | `FundingSkewStrategy` / `FundingSkewConfig` |
| `option_vol_selling.py` | `OptionVolStrategy` / `OptionVolConfig` |

Always have implementer subagents run a quick `grep -n "^class"` on the file before assuming names. Plans 4 (ml_fusion → `MLFusionStrategy`?), 5 (`FactorPortfolioStrategy`), 6 (`BasisArbStrategy`) — verify before each subagent dispatch.

### 6. Pragmatic integration test scope

Building synthetic NT-compatible parquet bars + a full BacktestNode invocation is significant work. Plans 1–3 settled on: **disk → parquet → panel/stream → strategy hook** integration tests (skip the NT engine). The CLI smoke tests in Tasks 9/10/11 of each plan already verified the engine path. This kept integration tests under ~100 lines each.

### 7. Capture scripts have no unit tests

`scripts/capture_orderbook.py` and `scripts/capture_option_summary.py` are long-running WS/REST loops. They're tested only via `--help` verification + manual smoke. Don't try to unit-test them; they're operational tools.

### 8. WS / REST API field-name drift

`OrderBook.ts` (not `ts_ms`), `OptionSummary.mark_vol` (not `mark_iv`), `OptionSummary.fwd_px` (no `mark_price`), `FundingRate.funding_time: int` (not datetime). Always have implementer subagents `grep` the actual model fields before writing code that constructs them.

### 9. Optional-dep gating (Plan 4)

ml_fusion requires xgboost. Pattern in pyproject.toml:
```toml
[project.optional-dependencies]
ml-fusion = ["xgboost>=2.0"]
```
And in code: lazy `import xgboost` inside functions that need it. Strategy's `__init__` raises ImportError with clear "install with `pip install -e .[ml-fusion]`" if missing. ml_fusion strategy file already has this guard — Plan 4 just needs to wire the training script + add `feed_funding_panel` mirroring the Plan 1 pattern (since ml_fusion uses funding_z as a feature).

### 10. Plan 5 is small

factor_portfolio's research CLI already implements `_cmd_backtest_portfolio_online` (see `src/okx_trade/research/cli.py:301`). Plan 5 is mostly glue: a `_run_factor_portfolio` in `scripts/backtest.py` that calls into it + an `ensure_panel_cached` helper. Probably 2-3 hours of work if no surprises.
